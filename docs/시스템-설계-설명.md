# 시스템 설계 설명 — 자세 판정 · 실시간 그룹 · 타임랩스

> 학생(비개발자) 대상 발표용. 고1 눈높이 비유 중심, 대본으로 바로 읽을 수 있게 작성.

## 1. 자세 판정 — "AI의 눈 + 우리가 만든 수학 채점기"

자세 판정은 2단계로 나뉩니다. **AI가 보고, 수학이 채점합니다.**

**1단계 (보기)**: 구글의 컴퓨터 비전 라이브러리 **MediaPipe**가 웹캠 영상에서 코·귀·어깨 같은 **33개 관절의 좌표를 매 프레임 추적**합니다. 여기까지가 AI의 일이고, 이 모든 계산은 서버가 아니라 **사용자 기기 안에서** 실행됩니다. 영상은 단 한 장도 밖으로 나가지 않습니다.

**2단계 (채점)**: 그 좌표에 저희가 설계한 수학 판정기를 적용합니다. 핵심 아이디어는 세 가지입니다.

- **"내 기준"과 비교한다** — 사람마다 체형과 카메라 위치가 달라서 절대 기준은 오판이 많습니다. 그래서 시작할 때 5초간 **본인의 바른 자세를 기준으로 등록**하고, "평소 내 자세 대비 얼마나 무너졌는지"를 계산합니다. 예를 들어 거북목은 귀가 어깨보다 앞으로 나간 정도를 재는데, 감점이 시작되는 지점은 **어깨너비의 13%(약 5cm)** — 이 숫자는 저희가 정한 게 아니라 **자세 교정 논문 3편을 교차 분석해서** 뽑은 값입니다.
- **성급하게 잔소리하지 않는다** — 나쁜 자세가 **8초 이상 지속돼야** 경고합니다. 물건을 줍느라 잠깐 숙인 것까지 혼내면 아무도 안 쓰니까요. 반대로 좋아질 때는 빨리 회복시켜서, 상태가 좋음↔나쁨 사이에서 덜덜 떨리지 않게 만들었습니다(히스테리시스).
- **천천히 무너지는 것도 잡는다** — 실제 슬럼프 자세는 갑자기 오지 않고 몇 분에 걸쳐 서서히 옵니다. 그래서 6분 창의 앞부분 평균과 뒷부분 평균을 비교해 **"조금씩 가라앉는 추세"** 를 감지하고, 경고 대신 조용한 넛지("허리 한 번 펴볼까요?")를 줍니다.

이 결과가 100점 만점 점수와 좋음/주의/나쁨/자리비움 상태가 되고, 요정의 반응·타이머·통계가 전부 여기서 나옵니다.

## 2. 실시간 그룹 공부방 — 메시(P2P)의 실패와 SFU로의 전환

**처음에는 서버 없이 참가자끼리 영상을 직접 주고받는 메시(mesh) 방식으로 만들었습니다.** 저희 서버는 "누가 방에 있는지" 소개만 해주고(시그널링), 영상은 폰끼리 직접 흐르는 구조라 서버 부담이 없어 보였습니다.

**그런데 인원이 늘자 문제가 폭발했습니다.**

- 4명이 모이면 각자 **나머지 3명에게 자기 영상을 3번씩 따로 업로드**해야 합니다. 방 전체로는 연결이 12개. 업로드 대역폭도, 영상 인코딩도 3배가 되니 **폰이 뜨거워지고 배터리가 급격히 닳고 화면이 버벅였습니다.** 장시간 공부라는 우리 사용 조건과 정면충돌이었습니다.
- 새 사람이 입장할 때마다 **기존 전원과 연결을 새로 협상**해야 해서, 한 명의 네트워크가 불안하면 방 전체가 흔들렸습니다.

**그래서 SFU 방식으로 갈아탔습니다.** SFU는 중계 서버입니다 — 각자 영상을 **서버에 딱 한 번만 올리면, 서버가 복사해서 나머지에게 뿌려줍니다.** 인원이 몇 명이 되든 내 폰의 업로드는 항상 1개. 4명 기준으로 내 폰의 부담이 3분의 1이 됐고, 입장·퇴장도 서버와의 연결 하나만 관리하면 되니 안정해졌습니다.

저희는 이 SFU를 오픈소스 **LiveKit으로 직접 셀프 호스팅**했고, 영상 중계는 CPU를 많이 쓰는 작업이라 **전용 가상머신(VM)에 분리 배치**해서 화상방이 아무리 바빠도 로그인·기록 저장은 영향을 받지 않게 했습니다. 방 입장은 API 서버가 발급한 토큰(JWT)을 SFU가 검증하는 방식이라 허가된 사용자만 들어올 수 있습니다.

> 한 줄 요약: **"서버를 없앤 설계(메시)가 오히려 폰을 죽였고, 중계 서버 하나(SFU)를 두는 게 모두를 살렸다."**

### 예상 질문

- **"MCU 방식은 왜 안 썼나요?"** — MCU는 서버가 모든 영상을 하나로 합성해서 보내는 방식인데, 서버 비용이 크고 저희 규모엔 과합니다. SFU는 복사만 하고 합성은 안 해서 서버 부담과 화질의 균형이 좋습니다.
- **"셀프 호스팅은 왜?"** — 중계 서버의 동작 원리를 직접 다뤄보고 싶었고, 전용 VM 분리 배치로 부하 격리까지 설계할 수 있었습니다.

## 3. 타임랩스 공부 인증 — "기기 안의 작은 영상 공장"

공부를 마치면 그 세션이 30~90초 타임랩스 영상이 되어 인스타 스토리로 공유할 수 있습니다. 설계 포인트는 **서버가 영상을 전혀 만지지 않는다**는 것입니다.

1. **캡처** — 공부 중 **2초에 1장씩** 화면을 찍습니다. 자세 감지용 카메라가 이미 켜져 있으니 추가 비용이 거의 없고, **사람이 화면에 보일 때만** 찍어서 빈자리는 영상에 안 들어갑니다. 프레임에는 그 순간의 타이머·자세 점수를 함께 새깁니다.
2. **임시 저장** — 프레임은 브라우저의 로컬 저장소(IndexedDB)에 쌓입니다. 장시간 대응 장치: 프레임이 상한(90초 분량)에 닿으면 **절반을 솎아내고 캡처 간격을 2배로** 늘립니다. 1시간을 공부하든 4시간을 공부하든 결과물은 항상 적당한 길이가 됩니다.
3. **인코딩** — 종료 후 프레임들을 초당 30장으로 이어붙여 **기기 안에서 mp4 영상으로** 만듭니다.
4. **공유** — 완성 영상을 OS 공유 시트로 넘기면 사용자가 인스타를 선택해 스토리에 올립니다. 영상은 사용자가 저장할 때만 그 기기에 남습니다.

**왜 서버로 안 보냈을까?** 영상 처리를 서버로 가져가면 스토리지 비용, 업로드 트래픽, 작업 큐와 워커 같은 무거운 인프라가 전부 필요해집니다. 처리를 각자의 기기에 남겨서 그 복잡도를 통째로 제거했습니다 — 사용자가 1만 명이 되어도 이 기능의 서버 비용은 **0원**입니다.

## 세 기능을 관통하는 설계 철학

**"무거운 일은 각자의 기기가, 서버는 꼭 필요한 중계와 기록만."** 자세 판정도, 타임랩스도 기기 안에서 끝나고, 서버가 개입하는 건 영상 중계(SFU)와 기록 저장(DB)뿐입니다. 그래서 작은 서버 두 대로도 서비스 전체가 돌아갑니다.
