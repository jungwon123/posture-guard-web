# LiveKit 셀프호스팅 (기술 챌린지, 브랜치 `livekit-selfhost`)

> 시연은 **LiveKit Cloud 그대로**(기본 경로), 셀프호스트는 **옵트인 A/B**로 병행 실험한다.
> 목표: SFU를 남의 SaaS로만 쓰지 않고, 같은 오픈소스 서버를 우리 VM에서 직접 운영해 본다.

## 무엇이 어디에 떠 있나

| 구성 | 내용 |
|---|---|
| 서버 | `livekit-server` v1.13.4 (공식 GitHub 릴리스 바이너리) — `pg-api-vm`의 `/usr/local/bin` |
| 설정 | `/opt/livekit/config.yaml` (600) — 포트 7880(ws), 7881(tcp 폴백), UDP 50000-50200, `use_external_ip: true`, API 키 1쌍(VM에서 생성, 외부 유출 없음) |
| 서비스 | systemd `livekit.service` (enable, Restart=on-failure) |
| TLS | Caddy에 `lk.34-64-158-222.sslip.io` 사이트 추가 → localhost:7880 리버스 프록시 (wss 자동) |
| 방화벽 | GCP 룰 `livekit-rtc`: tcp:7881, udp:50000-50200 허용 |
| 토큰 | `pgapi` 드롭인 `/etc/systemd/system/pgapi.service.d/livekit-self.conf` 에 `LIVEKIT_SELF_URL/KEY/SECRET` — `/api/rtc-token` 이 `self: true` 요청일 때만 이 키로 서명해 셀프호스트 URL 반환 |

## A/B 전환 방법 (클라이언트)

- 폰/브라우저 주소창에 `?lkself=1` 붙여 접속 → 이후 그리드 접속이 셀프호스트로. `?lkself=0` 으로 원복.
- 내부 동작: `localStorage.pg_lk_self=1` → GroupGridRoom 이 rtc-token 요청에 `self: true` 전달.
- 서버 기본값은 항상 Cloud — 플래그 없는 사용자는 아무 영향 없음.

## 검증된 것 (2026-07-22)

- 기본 경로: rtc-token → `wss://fairy-*.livekit.cloud` (변화 없음, `selfHosted:false`)
- 옵트인: rtc-token `self:true` → `wss://lk.34-64-158-222.sslip.io` + 셀프호스트 서버가 JWT 서명 검증 통과(JoinResponse 수신)까지 e2e 확인
- 남은 실기기 확인: 폰 2대(`?lkself=1`)로 영상 타일·점수 배지·콕 — 특히 **학교 와이파이에서 UDP 차단 시 tcp 7881 폴백**이 되는지. 안 되면 TURN(coturn) 추가가 다음 챌린지.

## 운영 주의

- **비용**: 셀프호스트 영상은 GCP 이그레스 요금이 든다(N명 방 = N×(N-1)×비트레이트). 실험은 짧게, 시연은 Cloud로.
- **리소스**: e2-small(2GB)이라 소규모 방(2~5명) 실험용. 반 전체는 Cloud 권장.
- **원복**: 클라이언트 `?lkself=0`. 서버를 아예 끄려면 `sudo systemctl disable --now livekit` (pgapi·Cloud 경로는 영향 없음).
- VM 삭제 시 같이 사라짐 — 발표 자료 캡처(systemd status, config, e2e 로그)는 미리.

## 발표 포인트 (mesh → SFU → 셀프호스트 3단 서사)

1. P2P mesh 직접 구현 (시그널링 서버 자작) → 업링크 N-1 구조 한계
2. SFU 전환 (LiveKit Cloud) → 반 전체 그리드
3. 같은 SFU를 **직접 운영** (오픈소스 서버 + TLS + 방화벽 + 토큰 서명) → 인프라 이해까지
