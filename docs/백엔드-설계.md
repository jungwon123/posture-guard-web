# 백엔드 설계 — 척추요정

> 원칙 1페이지: **감지 파이프라인(영상·랜드마크·신호·기준값)은 영원히 로컬.**
> 서버로 가는 것은 "닉네임 + 집계 숫자"뿐. 이 선이 우리 서비스의 차별점이다.

## 기술 스택 (GCP VM — 백엔드 인프라 직접 운영 학습)

현재 운영: **VM(Compute Engine)에 앱+DB를 직접 설치**. 2주 한정 실사용/학습용.
(이전: Cloud Run+Firestore 서버리스 버전 `backend/`는 참고용으로 보존)

| 층 | 선택 | 이유 |
|---|---|---|
| 서버 | **GCP Compute Engine VM** (e2-small, Debian 12, 서울) | 리눅스·컨테이너·DB 직접 운영 학습. 예산 $50 / 2주(~$8 예상) |
| 앱 | `backend-vm/` Express + `pg` — **Docker Compose 컨테이너** (`infra/`) | Cloud Run 버전과 API 계약 동일. 컨테이너 5종(nginx·api·db·redis·livekit) 한 스택 |
| DB | **PostgreSQL 16 컨테이너** (pgdata 볼륨) | 직접 운영 — 마이그레이션·pg_dump 백업 학습 |
| 캐시 | **Redis 7 컨테이너** (64MB LRU) | presence TTL 90초 + 리더보드 캐시 30초 — 논문의 Redis 캐시 제안 실현. 장애 시 DB·메모리 폴백 |
| HTTPS | **nginx** 게이트웨이 + certbot(Let's Encrypt) + **sslip.io** 호스트 | TLS 종료·WebSocket 프록시·인증 엔드포인트 rate limit. 도메인 없이 인증서 발급 |
| 인증 | 1단계 없음 → **익명 기기 ID(UUID) + 닉네임** | 로그인은 마지막 단계(로드맵 ③) |

- VM: `pg-api-vm` / zone `asia-northeast3-a` / 외부 IP 34.64.158.222
- API 주소: `https://34-64-158-222.sslip.io` (IP.sslip.io → 그 IP로 해석)
- 자동 설정: VM 부팅 시 startup-script가 Node·Postgres·Caddy 설치 + 앱 배포 (로그 `/var/log/pg-setup.log`)
- **정지/삭제(비용 종료)**: `gcloud compute instances delete pg-api-vm --zone asia-northeast3-a`
- 스키마: `groups(code,name)` · `members(id=UUID, nickname, group_id)` · `weekly_stats(member_id, week, good_sec, points)`

## 도입 로드맵

| 단계 | 내용 | 상태 |
|---|---|---|
| ① 그룹 랭킹 (로그인 없음) | 그룹 생성/참여(6자리 코드), 주간 "바른 자세 시간" 리더보드, 5분마다 집계 업로드 | **지금 구현** |
| ② 푸시 리마인더 | Web Push(VAPID) — "오늘 아직 안 켰어요", 그룹 소식. 아이폰 알림의 정석 경로 | 다음 |
| ③ 계정 (로그인) | 닉네임+복구코드 수준 초경량 → 기기 바꿔도 포인트·기록 유지. 익명 ID를 계정에 병합 | **가장 나중** |
| ④ 튜닝 데이터 수집 | 옵트인 익명 전이 로그 + 오탐 신고 → M3 오탐률 자동 측정 | 병행 가능 |

## 데이터 모델 (1단계)

```sql
groups        (id, code UNIQUE, name, created_at)          -- 코드 6자리 A-Z2-9
members       (id TEXT PK, nickname, group_id FK, created_at)  -- id = 기기 익명 UUID
weekly_stats  (member_id FK, week, good_sec, points, updated_at, PK(member_id, week))
              -- week = 그 주 월요일 날짜 "YYYY-MM-DD"
```

## API (1단계)

| 메서드/경로 | 입력 | 동작 |
|---|---|---|
| POST `/api/group` | `{name}` | 그룹 생성 → `{code, name}` |
| POST `/api/join` | `{code, nickname, memberId}` | 참여 (멤버 upsert, 닉네임 변경 겸용) |
| POST `/api/stats` | `{memberId, week, goodSec, points}` | 주간 집계 upsert (서버가 상한 클램프) |
| GET `/api/leaderboard?code=&week=` | — | 그룹 주간 순위 (good_sec 내림차순, 50명) |

- 스키마는 함수 콜드스타트 시 `CREATE TABLE IF NOT EXISTS`로 보장 (마이그레이션 도구는 이 규모에선 과함)
- 클라이언트: `pg_member_id`(UUID) 자동 생성, 가입 그룹은 `pg_group`에 저장, 업로드는 앱 시작 + 5분 주기 + 그룹 패널 열 때

## 공개 서비스 대비 (9명 아님 — 불특정 사용자 전제)

구현돼 있는 방어선:
- **레이트 리밋** (IP별): 전체 분당 120회, 그룹 생성은 시간당 10회
- **그룹 정원** 100명 (Firestore count 쿼리로 검사)
- **리더보드 인메모리 캐시 30초** — 조회 1회 = Firestore 읽기 (1 + 인원수)라서 캐시가 읽기 비용의 핵심. 인스턴스별 캐시(5,000키 상한)
- **Cloud Run `--max-instances 3`** — 트래픽 폭주 시 비용 상한
- 집계 상한 클램프 (주 403,200초 / 100,000P)

무료 한도 산수 (Firestore: 일 읽기 5만·쓰기 2만):
- 쓰기: stats 업로드 5분 주기 × 하루 8시간 사용 ≈ 사용자당 96회/일 → **약 200명까지 무료**. 초과 시 1차 대응은 업로드 주기 완화(5→15분)
- 읽기: 캐시 30초 덕분에 그룹당 최대 2회/분 × 인원수 — 수천 명 규모까지 여유

| 스택 | 지금 | 추가 시점 |
|---|---|---|
| 캐시 (Redis 등) | 인메모리 30초 캐싱으로 대체 (구현됨) | 다중 인스턴스에서 캐시 정합이 문제되거나 조회가 더 커질 때 |
| 스케줄러 (Cloud Scheduler) | ✗ — 주간 리셋은 week 키 설계로 불필요, 데이터 정리는 Firestore TTL | 로드맵 ② 푸시 리마인더 구현 시 (매일 저녁 발송 트리거, 무료 3개) |
| 예산 알림 (Billing Budget) | 권장 — 월 예산 알림 설정은 결제 계정 소유자가 콘솔에서 | 공개 홍보 전 필수 |

## 무결성 (랭킹 치팅 방어선)

감지가 클라이언트라 완전 방지는 불가 — 현실적 상한으로 방어:
- `good_sec` ≤ 403,200 (주 7일×16시간), `points` ≤ 100,000 — 서버에서 클램프
- 주간 값은 upsert(덮어쓰기)라 반복 업로드로 불어나지 않음
- 로그인(③) 도입 시 적립 검증을 서버 권위로 이관 검토

## 서버로 절대 안 가는 것

영상 프레임 · 포즈 랜드마크 · 신호 원본 · 캘리브레이션 기준값(μ,σ) · 녹화 JSON.
전이 로그는 ④에서 **옵트인 + 익명**일 때만.
